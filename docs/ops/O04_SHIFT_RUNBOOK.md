# راهنمای بهره‌برداری اپ شیفت

> نسخه 1.3 · ۱۴۰۵/۰۸/۰۹ · مبنا: `docs/shift/S02` (بخش ۴ و ۵)، `docs/ops/O01` (ADR-008)، ADR-014، ADR-015 و ADR-023، گام ۱۴ طراحی
> دامنه: `apps/shift` روی رایانهٔ درمانگاه. همهٔ دستورها از پوشهٔ `apps/shift` اجرا می‌شوند.

## ۱. پیش‌نیازها

| مورد | مقدار |
|---|---|
| Python | 3.13 (روی ویندوز؛ `py -3.13`) |
| مسیر داده | `shift.db` کنار اپ، بیرون از گیت (ADR-006) |
| لاگ‌ها | `logs/shift.log` (عمومی) و `logs/audit.log` (حسابرسی) — همیشه دو فایل جدا |
| پورت | 8443 (قابل تغییر با `SHIFT_PORT`)، فقط روی شبکهٔ درمانگاه |
| کاربر ویندوز | یک حساب اختصاصی که مالک `shift.db` و پوشهٔ پشتیبان است |

## ۲. نصب و راه‌اندازی نخست

1. کد را در مسیر عملیاتی کپی کنید و وابستگی‌ها را نصب کنید:
   `./dev.ps1 setup` (venv می‌سازد و `requirements-dev.lock` را نصب می‌کند؛ در پروداکشن فقط `requirements.lock` لازم است).
2. متغیرهای محیطی را تنظیم کنید (اختیاری؛ پیش‌فرض‌ها کنار خود اپ هستند):

   | متغیر | پیش‌فرض | کار |
   |---|---|---|
   | `SHIFT_HOME` | ریشهٔ `apps/shift` | مبنای همهٔ مسیرهای پیش‌فرض |
   | `SHIFT_DB_PATH` | `<SHIFT_HOME>/shift.db` | فایل دیتابیس |
   | `SHIFT_LOG_DIR` | `<SHIFT_HOME>/logs` | لاگ عمومی |
   | `SHIFT_AUDIT_LOG` | `logs/audit.log` | لاگ حسابرسی — هرگز با لاگ عمومی یکی نشود |
   | `SHIFT_SECRET_FILE` | `<SHIFT_HOME>/.shift_secret_key` | کلید امضای نشست؛ یک‌بار ساخته می‌شود |
   | `SHIFT_HOST` / `SHIFT_PORT` | `127.0.0.1` / `8443` | آدرس شنود |
   | `SHIFT_HASH_CHAIN` | `1` | زنجیرهٔ هش رویدادها |
   | `SHIFT_ENV` | `production` | پیش‌فرض تولید است: کوکی‌ها `Secure` می‌شوند و `/docs` و `/openapi.json` خاموش‌اند. فقط برای آزمون روی HTTP خام و بدون Caddy مقدار `development` بدهید؛ روی رایانهٔ درمانگاه هرگز |

3. دیتابیس و فهرست مرجع را بسازید (یک‌بار؛ پوشهٔ خالی کافی است). این دستور schema را migrate می‌کند و ۶ محل و ۸۳ قلم مرجع را می‌ریزد؛ اجرای دوباره بی‌خطر است:

   ```powershell
   .venv/Scripts/python.exe tools/seed_reference_data.py --db shift.db
   ```

   حداقل موجودی و کد حسابداری هر قلم را مدیر بعداً در `/manager/items` پر می‌کند (Q-17).
4. **نخستین مدیر** را بسازید. PIN را خود ابزار دو بار و پنهان می‌پرسد (از خط فرمان گرفته نمی‌شود و جایی چاپ یا لاگ نمی‌شود)؛ شش رقم و غیرقابل‌حدس باشد. ابزار را با همان متغیرهای `SHIFT_*` سرویس اجرا کنید تا همان دیتابیس و همان `.shift_secret_key` استفاده شود:

   ```powershell
   .venv/Scripts/python.exe tools/create_staff.py --name "<نام و نام خانوادگی>" --mobile 09xxxxxxxxx --role manager --staff-id manager
   ```

   `--role` تکراری می‌تواند چند نقش بدهد (`reception`, `nurse`, `storekeeper`, `purchaser`, `accountant`, `shift_doctor`, `manager`). موبایل نام ورود است و یکتاست. بقیهٔ پرسنل را همین ابزار می‌سازد (مدیر فعلاً صفحهٔ ساخت کارمند ندارد؛ فقط بازنشانی PIN، قفل‌گشایی و ثبت گوشی دارد).
5. سرویس را اجرا کنید: `./dev.ps1 run` (یا `.venv/Scripts/python.exe start.py`). در استارت، migrationها خودکار اجرا می‌شوند (`PRAGMA user_version`).
   اگر دیتابیس از قبل داده داشته باشد، **پیش از** هر migration یک snapshot در `backups/shift_pre_migration_<UTC>.db` گرفته می‌شود؛
   اگر backup یا migration شکست بخورد، سرویس بالا نمی‌آید (`MigrationError`) و هیچ تغییری نیمه‌کاره نمی‌ماند.
6. بررسی سلامت: `GET /healthz` باید `{"status": "ok", "version": "..."}` برگرداند؛ `/docs` و `/openapi.json` باید ۴۰۴ بدهند.
7. با سرویس روشن، گوشی مدیر را جفت کنید (بخش ۲.۱): `tools/print_enroll_qr.py --staff-id manager --origin https://<host> --out manager.svg`، سپس QR را روی گوشی باز کنید.
8. برای اجرای دائمی و HTTPS، بخش ۲.۲ را انجام دهید.

> **HTTPS:** سرویس خودش روی `127.0.0.1` HTTP ساده حرف می‌زند و Caddy (CA داخلی، ADR-015) روی همان رایانه HTTPS را به آن می‌رساند. کوکی‌های نشست در حالت تولید همیشه `Secure` هستند، پس بدون Caddy مرورگرِ گوشی ورود را نمی‌پذیرد؛ فقط Chrome روی `127.0.0.1` همان رایانه استثناست.

## ۲.۲ اجرای دائمی و HTTPS روی رایانهٔ درمانگاه

> این دو فایل هنوز با Caddy و NSSM واقعی اجرا نشده‌اند؛ روی رایانهٔ درمانگاه یک بار با حوصله امتحان و نتیجه اینجا ثبت شود.

1. به رایانه یک **IP ثابت** در شبکهٔ داخلی بدهید.
2. `caddy.exe` و `nssm.exe` را از سایت رسمی‌شان در یک پوشه بگذارید.
3. PowerShell را با دسترسی مدیر باز کنید و از پوشهٔ `apps/shift/deploy` اجرا کنید:

   ```powershell
   ./install-services.ps1 -Site 192.168.1.10 -AppDir C:/ShiftApp/apps/shift -DataDir C:/ShiftData -ToolsDir C:/ShiftTools -AccountingDb C:/Hesabdari/clinic_new.db
   ```

   دو سرویس `ShiftApp` و `ShiftCaddy` با روشن شدن رایانه بالا می‌آیند، و فقط پورت‌های ۸۰ و ۴۴۳ در فایروال باز می‌شوند. داده و کلید نشست در `-DataDir` است، پس **همان `SHIFT_HOME` را هنگام اجرای ابزارهای بخش ۲ هم تنظیم کنید**.
4. **روی هر گوشی، یک بار:** `http://<IP>/ca.crt` را باز کنید، گواهی را نصب و معتمد کنید. بعد `https://<IP>/` باید بدون هشدار باز شود.
5. نشانی‌های ثبت گوشی از این پس `https://<IP>` است، نه پورت 8443.

**برگشت:** `nssm remove ShiftApp confirm` و `nssm remove ShiftCaddy confirm`. دیتابیس دست نمی‌خورد.

## ۲.۳ HTTPS با پایتون، بدون Caddy و NSSM (ADR-023)

> مسیر رسمی همان بخش ۲.۲ است. این گزینه برای رایانه‌ای است که Caddy و NSSM روی آن نیست: یک پروسهٔ پایتون با **همان مدل اعتماد** (CA داخلی) و **بدون هیچ دانلودی**.

1. یک **IP ثابت** به رایانه بدهید (بند ۱ بخش ۲.۲).
2. از پوشهٔ `apps/shift`، با همان venv و همان `SHIFT_HOME`:

   ```powershell
   .venv/Scripts/python.exe deploy/serve_lan.py --home C:/ShiftData --ip 192.168.1.10
   ```

   اختیاری: `--name shift.local` (نام دوم گواهی)، `--https-port 8443`، `--http-port 8080`.
3. در استارت دو نشانی چاپ می‌شود: `https://<IP>:8443/` و `http://<IP>:8080/ca.crt`؛ هیچ کلید یا رمزی چاپ نمی‌شود. اپ همیشه با `SHIFT_ENV=production` بالا می‌آید.
4. **روی هر گوشی، یک بار:** `http://<IP>:8080/ca.crt` را نصب و معتمد کنید (صفحهٔ `/` همین را با پیوند فارسی نشان می‌دهد)، بعد `https://<IP>:8443/` را باز کنید. هر نشانی دیگری روی HTTP خودکار به HTTPS می‌رود.
5. توقف: `Ctrl+C` — هر دو شنونده تمیز بسته می‌شوند.

| مورد | مقدار |
|---|---|
| ریشهٔ CA | `<home>/tls/ca.crt` و `ca.key`؛ ۱۰ سال، `CA:TRUE`، `keyCertSign` + `cRLSign` |
| گواهی سرور | `<home>/tls/server.crt` و `server.key`؛ حداکثر ۳۹۷ روز (سقف Android Chrome)، `serverAuth` |
| SAN | `IP:<ip>`، `IP:127.0.0.1`، `DNS:<name>`، `DNS:localhost` |
| بازصدور | با هر تغییر IP یا نام، و ۳۰ روز پیش از انقضا؛ **همیشه با همان ریشه**، پس گوشی چیزی دوباره نصب نمی‌کند |
| کلیدها | فقط زیر `<home>/tls`؛ روی ویندوز ACL پوشه نگهبان واقعی است |
| ساخت گواهی | `cryptography` اگر در venv باشد، وگرنه `openssl` از PATH (بدون وابستگی تازه) |

- کوکی‌های نشست همچنان `Secure` و `SameSite=Strict` هستند و `/docs` و `/openapi.json` خاموش می‌مانند؛ این مسیر هیچ تنظیم امنیتی را سست نمی‌کند. `X-Forwarded-*` فقط از `127.0.0.1` (پروکسی محلی) باور می‌شود، نه از گوشی‌های شبکه.
- پورت‌های ۸۴۴۳ و ۸۰۸۰ باید در فایروال ویندوز برای شبکهٔ خصوصی باز باشند؛ اگر ۸۰۸۰ روی این رایانه گرفته شده (مثلاً Docker)، `--http-port` دیگری بدهید و همان را به گوشی‌ها بگویید.
- این فرمان سرویس ویندوز نمی‌سازد؛ برای بالا آمدن با روشن شدن رایانه، بند ۳ بخش ۲.۲ (NSSM) یا یک وظیفهٔ Task Scheduler لازم است.

## ۲.۱ ثبت گوشی پرسنل با QR (device enrollment)

هر گوشی یک بار به یک کارمند جفت می‌شود. QR فقط همین کار را می‌کند؛ ورود روزانه همیشه با موبایل و PIN است (ADR-012، ADR-014).

**پیش‌نیاز:** کارمند در `staff` هست و فعال است؛ گوشی نشانی **HTTPS** داخلی (Caddy، ADR-015) را با گواهی ریشهٔ نصب‌شده باز می‌کند، چون صفحهٔ ثبت بدون Secure Context بالا نمی‌آید (`crypto.subtle`).

**راه ۱ — صفحهٔ مدیر:** با حساب مدیر وارد شوید ← `/admin/devices` ← کارمند را انتخاب کنید ← «ساخت کد ثبت دستگاه». QR و اعتبارش نمایش داده می‌شود. روی گوشی همان کارمند اسکن کنید (یا همان نشانی را باز کنید) ← نام گوشی را بنویسید ← «ثبت دستگاه» ← پیام «این گوشی ثبت شد» و پیوند ورود.

**راه ۲ — خط فرمان (از `apps/shift`):**

```powershell
.venv/Scripts/python.exe tools/print_enroll_qr.py --db shift.db --staff-id <staff_id> --origin https://<host> --out "D:/sib-ops/enroll/<staff_id>.svg"
```

| خروجی | معنا |
|---|---|
| `device_id`، `staff_id`، `valid_to` (جلالی، تهران)، `url` | کد ساخته شد؛ `valid_to` ده دقیقه بعد از ساخت است |
| فایل `--out` | تصویر QR؛ پسوند `.svg` یا `.png` را از نام فایل می‌گیرد. بدون `--out` همان QR در کنسول چاپ می‌شود |
| `cannot mint an enrollment token: <staff_id>` | کارمند نیست یا غیرفعال است (کد خروجی ۱) |
| `database not found: <path>` | مسیر `--db` غلط است (کد خروجی ۱) |

- `--origin` همان نشانی‌ای است که گوشی می‌بیند؛ توکن در قطعهٔ `#t=` نشانی می‌نشیند، پس در لاگ وب‌سرور، لاگ پروکسی و سرآیند Referer ثبت نمی‌شود.
- `--created-by` (پیش‌فرض `cli`) روی توکن ثبت می‌شود؛ نام اپراتور را بگذارید.
- نوشتن روی همان `shift.db` است (WAL)، پس لازم نیست سرویس را خاموش کنید؛ اگر `database is locked` دیدید، چند لحظه بعد دوباره اجرا کنید.
- در دیتابیس فقط SHA-256 توکن ذخیره می‌شود؛ خود توکن جایی ذخیره نمی‌شود.

**قواعد امنیتی:** توکن یک‌بارمصرف و ۱۰ دقیقه‌ای است؛ یک QR = یک گوشی و اسکن دوم رد می‌شود. نشانی چاپ‌شده و فایل QR تا لحظهٔ انقضا مثل رمز هستند؛ آن‌ها را جایی نفرستید و در هیچ سندی نگذارید. توکن منقضی یا مصرف‌شده ← از مدیر کد تازه بگیرید.

**لغو گوشی گم‌شده:** `/admin/devices` ← «لغو دسترسی». دستگاه لغو می‌شود و نشست‌های بازش دیگر پذیرفته نمی‌شوند.

## ۳. پشتیبان‌گیری (backup)

```powershell
.venv/Scripts/python.exe tools/backup_now.py --db shift.db --to "D:/sib-backup/shift" --mirror "\\nas\sib\shift" --keep 7
```

| مرحله | چه می‌کند |
|---|---|
| `PRAGMA wal_checkpoint(TRUNCATE)` | WAL را در فایل اصلی جمع می‌کند؛ اگر خواننده‌ای مشغول باشد فقط هشدار می‌دهد و ادامه می‌دهد |
| `sqlite3 backup()` | کپی آنلاین و سازگار از دیتابیس زندهٔ WAL (کپی فایلی ساده ممنوع — شکاف S6) |
| `journal_mode = DELETE` روی کپی | snapshot یک فایل خودکفا می‌شود؛ `-wal` و `-shm` پشت سر نمی‌ماند |
| `PRAGMA integrity_check` + شمارش رویدادها | تا سالم نبود، کپی «پشتیبان» شمرده نمی‌شود؛ فایل ناسالم (`*.partial`) پاک می‌شود |
| مکان دوم (`--mirror`) | همان فایل به دیسک دوم/شبکه کپی و **دوباره** بررسی می‌شود |
| نگه‌داری (`--keep`) | فقط آخرین N نسخه در هر مکان می‌ماند؛ snapshotهای پیش از migration هرگز خودکار پاک نمی‌شوند |

- نام فایل: `shift_<YYYYMMDDTHHMMSSffffffZ>.db` (UTC) — ترتیب الفبایی = ترتیب زمانی.
- خروجی: کد ۰ یعنی snapshot سالم در هر دو مکان ساخته شد؛ کد ۱ یعنی کپی رد شد (پیام `backup rejected: ...`).
- زمان‌بندی پیشنهادی: هر روز یک‌بار پس از پایان شیفت شب (مثلاً ۰۸:۰۰) و یک‌بار پیش از هر انتشار.
  RPO/RTO و سیاست کامل در `O01` بخش ۲ است.
- پس از هر پشتیبان‌گیری دستی، یک سطر در جدول تمرین بازیابی (`O01` بخش ۳) ثبت کنید.

## ۴. زمان‌بندی کارهای دوره‌ای (scheduler)

| کار | زمان | قاعده |
|---|---|---|
| کارت روزانهٔ مدیر | ۰۷:۳۰ تهران | جمعه کارت ندارد؛ کارت شنبه دو روز (جمعه و شنبه) را پوشش می‌دهد (S01 بخش ۶) |
| هشدار شمارش هفتگی انبار | دوشنبه | شمارش هفتگی از شنبه تا دوشنبه انجام می‌شود؛ انجام‌نشدنش هشدار دارد (S01 بخش ۴) |

- ساعت هر کار **در کد ثابت نیست**: از تنظیمات نسخه‌دار (`ScheduleSettings`) خوانده می‌شود تا تغییر ساعت نیاز به انتشار نداشته باشد (R-09). تنها استثنا روز بی‌کارت است: جمعه، که طبق S01 بخش ۶ در کد ثابت است و تنظیمی برای عوض‌کردنش نیست (ADR-018).
- هر کار در هر دوره (روز برای کارت، هفتهٔ ISO برای هشدار) فقط یک‌بار اجرا می‌شود؛ اگر سرویس در آن لحظه خاموش بوده، در نخستین بررسی بعدی جبران می‌شود.
- در این گام فقط «چه‌وقت» پیاده شده است؛ متن کارت و متن هشدار در گام‌های SHF-6.1 و SHF-4.x می‌آیند.

## ۵. لاگ حسابرسی (audit)

- دو مقصد، همیشه جدا: جدول `audit_log` داخل `shift.db` و فایل `logs/audit.log`.
  چیزی که در audit ثبت می‌شود **هرگز** در `logs/shift.log` نمی‌آید (`services/audit.py` تنها از sink حسابرسی استفاده می‌کند؛ S02 بخش ۳.۲).
- عدد مرجع شمارش کور (R-02) فقط اینجا مجاز است، نه در لاگ عمومی و نه در پاسخ API.
- جدول `audit_log` فقط‌افزودنی است: triggerها هر `UPDATE` و `DELETE` را با خطای `append-only` رد می‌کنند (migration `m0005_audit_log`).
- ستون‌های `actor_id`, `action`, `outcome` (`ok|denied|failed`), `subject_id`, `detail` (JSON) و دو زمان `at_utc` و `at_tehran`.
- بررسی سریع:

  ```powershell
  .venv/Scripts/python.exe -c "import sqlite3;c=sqlite3.connect('file:shift.db?mode=ro',uri=True);print(c.execute('SELECT id,at_tehran,actor_id,action,outcome FROM audit_log ORDER BY id DESC LIMIT 20').fetchall())"
  ```

- چرخش فایل: هر فایل تا ۱۰ مگابایت، ۵ نسخه (`config/logging.py`). `detail` هیچ‌گاه رمز/PIN/توکن ندارد؛ سرویس حسابرسی چنین ورودی‌هایی را رد می‌کند.

## ۶. بازبینی زنجیرهٔ رویدادها (verify event chain)

```powershell
./dev.ps1 verify                                    # روی دیتابیس پیش‌فرض
.venv/Scripts/python.exe tools/verify_event_chain.py --db shift.db --no-links   # اگر SHIFT_HASH_CHAIN=0
```

- خروجی سالم: `chain ok: <n> events` (کد ۰). اولین شکست: `chain broken at seq <n>: <reason>` (کد ۱).
- triggerها را مالک دیتابیس می‌تواند حذف کند؛ کنترل واقعی، همان زنجیرهٔ هش + پشتیبان‌های بیرونی است.

```powershell
.venv/Scripts/python.exe tools/rebuild_projections.py --db shift.db --apply    # بازسازی و جایگزینی
```

1. **اول** پشتیبان بگیرید (بخش ۳).
2. بدون `--apply` اجرا کنید: برای هر projection مقدار `live` و `rebuilt` چاپ می‌شود؛ اگر برابر باشند کد ۰.
3. اگر `drift detected` دیدید، پیش از `--apply` علت را بفهمید (نسخهٔ کد قدیمی‌تر، رویداد دست‌کاری‌شده، یا باگ) و در `O02` ثبت کنید.
4. `--apply` جدول‌های سایه را می‌سازد، از رویدادها پر می‌کند و فقط در صورت موفقیت جایگزین می‌کند؛ پس از آن دوباره بدون `--apply` بررسی کنید.

## ۸. بازیابی (restore)

1. سرویس را ببندید (هیچ نویسنده‌ای روی دیتابیس نماند).
2. فایل خراب را پاک نکنید؛ تغییر نام دهید: `shift.db` → `backups/broken_<UTC>.db` و `shift.db-wal` و `shift.db-shm` را هم کنار بگذارید.
3. snapshot را **پیش از** کپی بررسی کنید:

   ```powershell
   .venv/Scripts/python.exe tools/restore_check.py --backup "D:/sib-backup/shift/shift_20261028T090000000000Z.db"
   ```

   این ابزار فایل را فقط‌خواندنی باز می‌کند و سه چیز را می‌سنجد: `integrity_check`، نسخهٔ schema (نباید از کد جلوتر باشد)، و زنجیرهٔ هش رویدادها. کد ۰ = قابل بازیابی.
4. فایل سالم را به مسیر `SHIFT_DB_PATH` کپی کنید. snapshot تک‌فایلی است؛ کنارش `-wal`/`-shm` نگذارید.
5. سرویس را بالا بیاورید؛ سپس `./dev.ps1 verify` و `rebuild_projections.py` (بدون `--apply`) را اجرا کنید.
6. رویدادهای بین زمان snapshot و خرابی را از روی برگهٔ کاغذی/لاگ ثبت کنید (O02 بخش ۲).
7. حادثه را در `O02` و تمرین بازیابی را در `O01` بخش ۳ ثبت کنید.

## ۹. بازبینی ماهانه

| کار | دستور | انتظار |
|---|---|---|
| بازیابی آزمایشی | `restore_check.py --backup <جدیدترین>` | کد ۰، تعداد رویداد معقول |
| زنجیره | `./dev.ps1 verify` | `chain ok` |
| projectionها | `rebuild_projections.py` (dry run) | بدون drift |
| مکانی دوم پشتیبان | مقایسهٔ فهرست دو پوشه | هر دو snapshot امروز را دارند |

## ۱۰. عیب‌یابی سریع

| نشانه | علت محتمل | کار |
|---|---|---|
| `database is locked` | نویسندهٔ دوم یا خوانندهٔ طولانی | سرویس را تنها نمونه کنید؛ `busy_timeout` ۵ ثانیه است (شکاف S2) |
| `backup rejected: ... failed integrity_check` | کپی ناسالم یا دیسک | فضای دیسک و سلامت دیسک را بررسی کنید؛ snapshot رد شده پاک شده است |
| `backup rejected: second location rejected ...` | شبکه/NAS قطع یا فایل قفل | مسیر `--mirror` را بررسی و دوباره اجرا کنید؛ نسخهٔ محلی سالم است |
| `wal_checkpoint is busy` در لاگ | خوانندهٔ فعال هنگام پشتیبان | طبیعی است؛ کپی همچنان سازگار است |
| `chain broken at seq <n>` | دست‌کاری یا بازگردانی ناقص | همان seq را با پشتیبان‌ها مقایسه کنید؛ حادثه S1 (O02) |
| `MigrationError` در استارت | migration شکست خورده | سرویس بالا نمی‌آید؛ snapshot پیش از migration را بررسی/بازیابی کنید |
| نبود `logs/audit.log` | مسیر `SHIFT_AUDIT_LOG` اشتباه یا بی‌مجوز | مسیر و دسترسی کاربر سرویس را درست کنید |
| `database not found: ...; run tools/seed_reference_data.py` | هنوز دیتابیس ساخته نشده | بند ۳ بخش ۲ |
| `refused: that staff id or mobile already exists` | موبایل یا شناسه قبلاً ثبت شده | موبایل دیگر یا `--staff-id` دیگر؛ برای بازنشانی PIN از صفحهٔ مدیر |
| `cannot mint an enrollment token: ...` | کارمند غیرفعال است یا `--staff-id` غلط | شناسه را در فهرست `/admin/devices` ببینید و درست بدهید (بخش ۲.۱) |
| `/enroll` می‌گوید «این صفحه باید روی نشانی امن (HTTPS) باز شود» | گوشی روی HTTP خام است یا گواهی ریشه نصب نیست | نشانی HTTPS با CA داخلی (ADR-015)؛ بخش ۲.۱ |
| `enrollment token rejected: expired` یا `used` | توکن ۱۰ دقیقه‌ای گذشته یا یک‌بار مصرف شده | از مدیر کد تازه بگیرید؛ هر QR فقط یک گوشی |
