# سازگاری با دیتابیس پروداکشن و مهاجرت‌ها

> نسخه 1.0 · ۱۴۰۵/۰۸/۰۴ · مبنا: ADR-002، ADR-008

## ۱. قانون طلایی

> **هر نسخهٔ جدید باید روی دیتابیس فعلی پروداکشن بدون دست‌کاری دستی بالا بیاید، و نسخهٔ قبلی باید روی دیتابیس مهاجرت‌یافته هم کار کند.**

بند دوم یعنی بازگشت همیشه ممکن است: اگر نسخهٔ جدید مشکل داشت، exe قبلی را برمی‌گردانیم و همان دیتابیس را باز می‌کنیم.

## ۲. تغییرات مجاز و ممنوع

| مجاز | ممنوع |
|---|---|
| جدول جدید | حذف یا تغییر نام جدول |
| ستون جدید nullable یا با DEFAULT | حذف، تغییر نام یا تغییر نوع ستون |
| index جدید | تغییر معنای مقدارهای موجود (مثلاً `status`) |
| view جدید (برای اپ شیفت) | `NOT NULL` جدید روی ستون موجود |
| trigger فقط‌ثبت‌کننده، مثل لاگ | trigger که داده را تغییر دهد |
| backfill ستون **جدید** | به‌روزرسانی انبوه ستون‌های قدیمی |

اگر روزی تغییر ممنوعی لازم شد، یک ADR جدید با برنامهٔ دو مرحله‌ای نوشته می‌شود (expand/contract در دو انتشار جدا، با تأیید مالک).

## ۳. سیستم مهاجرت

- نسخه در `PRAGMA user_version`. پروداکشن امروز = **0**.
- مهاجرت `0001_baseline` فقط کارهای `_ensure_*` فعلی را رسمی می‌کند: `work_date` و `shift`، `users.staff_id`، indexها و جدول `settings`. روی دیتابیس پروداکشن هیچ‌چیز جز `staff_id` و index آن را تغییر نمی‌دهد و `user_version` را ۱ می‌کند.
- هر مهاجرت یک فایل `NNNN_name.py` با تابع `up(conn)` است. `down` نداریم؛ بازگشت با پشتیبان یا با سازگاری رو به عقب انجام می‌شود.
- اجراکننده هنگام شروع برنامه:
  1. اگر `user_version` از آخرین مهاجرت کمتر است، **اول پشتیبان کامل** با backup API در `backups/pre_migration_vX_<time>.db` و `integrity_check` روی آن.
  2. هر مهاجرت در یک تراکنش. شکست ← rollback، لاگ، و **برنامه با پیام فارسی روشن بالا نمی‌آید** (به‌جای کار با schema ناقص).
  3. اگر `user_version` از نسخهٔ کد **بیشتر** است (exe قدیمی‌تر روی دیتابیس جدیدتر)، برنامه اجرا می‌شود ولی هیچ مهاجرتی اجرا نمی‌کند، و این در لاگ ثبت می‌شود.
- مهاجرت‌ها idempotent‌اند: دوبار اجرا = یک‌بار اجرا.

## ۴. تست‌های اجباری برای هر مهاجرت

| تست | دیتابیس | در CI؟ |
|---|---|---|
| روی دیتابیس خالی + `schema.sql`، که نتیجه‌اش باید با «پایه + همهٔ مهاجرت‌ها» یکسان باشد | خالی | بله |
| روی دیتابیس مصنوعی با schema نسخهٔ 0 | مصنوعی | بله |
| دوبار اجرا، بی‌تغییر | مصنوعی | بله |
| کد **قبلی** روی دیتابیس مهاجرت‌یافته؛ همهٔ تست‌های دود قبلی سبز | مصنوعی | بله |
| روی کپی پروداکشن: مهاجرت + همهٔ مسیرها + گولدن مستر بی‌اختلاف + `integrity_check` | کپی واقعی | **فقط محلی**، اجباری پیش از هر انتشار |
| زمان اجرا روی کپی پروداکشن کمتر از ۳۰ ثانیه | کپی واقعی | فقط محلی |

## ۵. مقایسهٔ schema

ابزار `tools/schema_diff.py` اسکیمای دو دیتابیس را مقایسه می‌کند (جدول، ستون، index) و هر تغییر غیرافزایشی را خطا می‌گیرد. در CI بین «خط پایهٔ پروداکشن» (فایل متنی schema، بدون داده، commit‌شده) و «پس از همهٔ مهاجرت‌ها» اجرا می‌شود.

## ۶. دسترسی اپ شیفت

اپ شیفت فقط از طریق viewهای نسخه‌دار می‌خواند (`v_shift_*`، S04). viewها بخشی از مهاجرت‌ها هستند و قرارداد آن‌ها تست دارد، تا تغییر داخلی جدول‌ها اپ شیفت را نشکند.

مهاجرت ۸ (۱۴۰۵/۰۸/۱۱، تصمیم ۵ مالک) دو view تازه اضافه می‌کند و هیچ جدولی را تغییر نمی‌دهد: `v_shift_patient_registrations_v2` همان ستون‌های v1 به‌همان ترتیب به‌علاوهٔ `first_for_phone` (۱ برای کمترین `patients.id` میان بیماران یک شمارهٔ معتبر، و ۱ هم وقتی شماره معتبر نیست)، و `v_shift_call_sample_v1` (نام کامل، موبایل، زمان و ثبت‌کنندهٔ بیماران با شمارهٔ معتبر) برای «نمونهٔ تماس» کارت مدیر. اپ شیفت از v2 پرچم تکرار موبایل را در آینه می‌گیرد و تا وقتی نصب حسابداری مهاجرت ۸ را ندارد v1 را می‌خواند و هر ثبت را اولین می‌شمارد؛ view نمونهٔ تماس را هم فقط هنگام رندر صفحهٔ مدیر و با اتصال فقط‌خواندنی می‌خواند و هیچ‌جا ذخیره نمی‌کند. حسابداری همچنان فقط هشدار تکرار موبایل را می‌دهد و هیچ ثبتی را رد نمی‌کند.
